# 聊聊逐輪延遲與連續性優化（2026-08-10）

## 目標與風險

本批次會影響 App 聊聊通話、Voice、Avatar/WebRTC 與插話，屬於 **call-path risk**。程式與合成測試只能證明候選行為，安裝指定版本的 iPhone App 完成真實通話前，狀態一律為 `App E2E pending`。

## 本批次行為

### 1. 自適應輪替等待

Gemini Automatic Activity Detection 的安靜基線設為 650ms；Voice 在收到完成轉錄後，只補足該輪所需的剩餘時間，不再把固定等待疊加：

| 使用者句型 | 總目標 | Voice 額外等待 |
|---|---:|---:|
| 明確完整句（含終止標點） | 650ms | 0ms |
| 一般對話 | 800ms | 150ms |
| 「嗯……／然後／可是」等未完句，或已觀察為慢速說話者 | 1100ms | 450ms |

慢速使用者判斷採同一通內的續說停頓 EWMA；至少觀察兩次後才延長，避免一次偶然停頓讓整通永久變慢。

部署時必須移除或更新舊的 `MUNEA_VOICE_SILENCE_MS=1100` 覆蓋值。保留舊值會讓程式中的 650ms 基線無效。

### 2. Avatar 動態預緩衝

- 每輪從 200ms 起步，上限 350ms。
- 只有播放中真正發生 underrun，下一輪才增加 50ms。
- 連續三輪穩定後下降 50ms，最低回到 200ms。
- GPU 計算 p95 僅保留為觀測資料，不再因計算較慢就預先把每句固定墊長。
- 程式會把所有相關環境值硬限制在 200–350ms；歷史 0.5–0.7 秒值不再能覆蓋此上限。部署時仍應把環境值同步清理，避免維運畫面與實際行為互相矛盾。

### 3. 真正逐輪碼錶

每輪帶相同 turn id，記錄五個節點：

1. 手機最後一次偵測到人聲
2. Voice 的 VAD stop／完成轉錄
3. Voice 收到模型首個 PCM
4. Avatar 收到該輪首個 PCM
5. App 的 WebRTC jitter buffer 已吐出本輪音訊，或遠端音訊已解碼且實際 Avatar 播放器正在啟用並出現有效音量

第 5 點必須先收到 Avatar 本輪首 PCM 回執，才會接受 `webrtc_jitter_buffer_emitted_player_active` 或 `decoded_remote_audio_player_active`；可排除上一輪殘音和只收到封包尚未播放的假陽性。這是瀏覽器可觀察到的最接近「真正播放」證據；Web API 無法直接量到 iPhone 實體喇叭振膜出聲時刻，因此不把它誤稱為硬體喇叭量測。

逐輪事件回報 `lastHumanToVadMs`、`vadToVoiceMs`、`voiceToAvatarMs`、`avatarToWebrtcMs` 與 `lastHumanToWebrtcMs`，用來定位第二輪以後究竟慢在哪一段。

### 4. 插話與卡頓／重複防護

- 一般輪：150ms 確認人聲＋100ms duck-confirm，目標完整停聲約 250ms。
- 開場前兩輪：190ms＋100ms，目標約 290ms。
- 保留先 duck 再停止，降低回音誤切；實際 stop 時重新計算完整確認耗時。
- Avatar 同線監測改為 200ms；400ms 微卡即留下證據。
- 多次微卡或開臉過慢，只在輪與輪之間切到 voice-only，不在句中切換音路。
- 健康守護與安全隱藏追問綁定真實使用者 turn id，不允許隱藏追問再次觸發自己的口語回答；「我沒有發燒但有痰」應只回答一次。
- 台語輸出攔截改採片語級強證據，避免單一不穩定串流片段造成整段重生與重複。

## 驗證與上線門檻

### 自動化預檢

- Python／JavaScript 語法檢查
- 650／800／1100 精確選擇與慢速使用者測試
- Avatar 實際 underrun 升檔及三輪穩定降檔測試
- 五節點逐輪事件與 WebRTC 播放 basis 測試
- 一般／開場插話總等待不超過 300ms 的政策測試
- 守護流程不自我觸發與重複回答測試
- 完整 `npm run test:launch`

### iPhone App E2E（尚未完成）

必須記錄 App 版本／Build、profile、Voice／Avatar／Gateway revision、iPhone 型號與時間，並完成：

1. 按通話、取得麥克風、通過 Auth／帳戶／點數與正式 Gateway。
2. Voice 與 Avatar ready，使用者先講第一句並收到可聽可見回應。
3. 連續至少五輪覆蓋完整句、一般句、未完句與慢速停頓。
4. 說「我沒有發燒但有痰」，確認只答一次且靜默後不自行重播。
5. 讓 AI 連續回答較長內容，確認沒有每句 1–2 字的斷續與重複。
6. 實測插話停聲；目標正常輪小於 300ms。
7. 掛斷並確認 Gateway／Avatar capacity 釋放。

## 後續：手機上行 WebRTC

手機到 Voice 的 WebRTC 上行屬於第二階段，未包含在本批次。先用逐輪碼錶確認固定等待已消失並建立穩定基線，再以小流量 A/B 導入；比較 `lastHumanToVadMs`、封包遺失、jitter、重連率、耗電與相同句子的首音時間，避免在沒有基準時同時改變等待與傳輸層。

## 回滾

- Voice 可將 AAD profile 回到 800ms，或以明確環境值暫時覆蓋。
- Avatar 如需超過 350ms，必須回退到前一個已驗版本；新版不允許環境值把每輪偷偷拉回 500–700ms。
- App 的 microstall voice-only fallback 可獨立關閉；不得在句中切換雙音路。
