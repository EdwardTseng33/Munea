## 0. 三個決定架構的判斷（思考順序）

**判斷一 · 就醫代理放在哪顆腦？→ 管家腦（背景），不是反射腦（熱路徑）。**
`產品遠景 §B-6` 已定調「深功夫放背景先做好，對話當下只取用已備好的 → 深而不慢」。摘要單的生成、症狀時間軸的彙整、口袋問題的整理，**全部是背景任務**（比照 `run_daily_briefing.py` 清晨備料），語音線只做兩件事：①把已備好的摘要「知道」②收下用戶新講的線索丟進背景。**任何會讓聊聊變慢的做法一律否決**——長輩等不了，這是既有鐵律。

**判斷二 · 資料模型缺的不是欄位，是「事件」這個維度。**
現有健康資料全是「以人為單位 × 以天為單位」（`family_state_entries` 的 365 天 log、`medication_dose_events` 的每日劑次、`memory_items` 的事實條目）。但就醫代理需要的是**以一次就醫為單位**的敘事：症狀何時開始 → 想問什麼 → 幾號看哪科 → 醫生說了什麼 → 後續怎麼追。這條線橫跨天、橫跨資料表，**現有模型接不起來**。這是 M1 唯一真正的新架構。

**判斷三 · 摘要單不是新功能，是既有能力的「換一個讀者」。**
`health_context.py` 已經在做「把數據翻成事實給寧寧看」，而且它的三條鐵律（跟自己比不跟量表比／講事實不講判定／沒資料就誠實回空）**跟摘要單需要的完全同構**——因為醫師要的正是「這個人跟他自己平常比，變了什麼」。所以摘要單＝`health_context` 的兄弟模組，讀者從「寧寧」換成「醫師」，鐵律一字不改。**不重寫、不另建一套健康資料管線。**

## 1. 架構主張：新增「就醫脈絡層」（Care Episode Layer）

```
                        ┌─────────────────────────────────┐
   既有三腦一臉          │      就醫脈絡層（新 · M1）        │
   ─────────────        │                                 │
   反射腦（語音熱路徑）──→│  care_episodes  一次就醫的敘事   │
     只讀已備好的        │  care_notes     線索/問題/醫囑    │
     只寫新線索          │                                 │
                        │  ↓ 產出                          │
   管家腦（背景）───────→│  就診摘要單（一頁 · 30秒可讀）    │
     生成/彙整/更新      │                                 │
                        └─────────────────────────────────┘
   守護腦（安全）────────→ 紅旗往上推（既有）＋不對稱鐵則（新增文字）
                                     ↑
   ┌─────────────────────────────────┴───────────────────┐
   │ 資料來源（全部既有、不新建管線）                        │
   │ family_state_entries（量測 log）· medication_dose_events（用藥實況）│
   │ memory_items(type=health_context)（症狀線索）· wellbeing_signals（心情）│
   │ munea.visits / routine_reminders（看診與用藥排程）       │
   └───────────────────────────────────────────────────────┘
```

**為什麼要獨立一層、不塞進既有表**：
- 塞 `routine_reminders.schedule` jsonb＝重演藥袋照片事故（`018_strip_medication_photos.sql`：jsonb 亂塞導致隱私承諾破功、事後要寫 migration 清）。
- 塞 `memory_items`＝污染記憶層語意（記憶是「關於這個人的事實」，不是「一次就醫的流程狀態」），且會被 `consolidate()` 的相似度合併吃掉。
- 就醫 episode 有**生命週期與狀態機**（醞釀中→已排診→已就診→追蹤中→結案），既有表都沒有這個語意。

## 2. 地基盤點（翻過程式碼的結論）

### 2-1. 可以直接複用的（M1 有一半是白撿的）

| 既有件 | 位置 | M1 怎麼用 |
|---|---|---|
| 健康事實翻譯＋三條鐵律 | `engine/health_context.py`（`baseline_and_recent`／`summarize_vitals`／`summarize_medication`／`NOISE_FLOOR`） | 摘要單的「跟平常比」段直接呼叫，**不重寫算法** |
| 症狀線索的萃取與分級 | `memory_engine.py` `TYPES` 已含 `health_context`；tier(core/long/recent/today)＋importance＋confidence | 症狀線索本來就在記，M1 只加「挑出來、排時間軸」 |
| 用藥實際順從度 | `medication_dose_events` 表＋`summarize_medication()` | 摘要單獨家欄位「開了藥有沒有真的吃」 |
| 看診提醒（語音可建檔） | `live_voice_server.py:702` `set_clinic_reminder` tool → `app.js:966` `aiAddVisitReminder` → `munea.visits` | M1 的 episode 掛在既有 visit 上，**不重做建檔 UX** |
| 看診推播 | `notification_service.py` `clinic_upcoming`＋`notify.js` 已有分類開關 | 「就診前一天摘要單備好了」用既有推播管線 |
| 背景備料管線 | `run_daily_briefing.py`＋`perception_snapshots`＋清晨鬧鐘（Cloud Scheduler 已上線） | 摘要單生成掛同一條，不新建排程基礎設施 |
| 同意紀錄基礎設施 | `consent_records` 表（`consent_type`／`version`／`scope`／`evidence`／`status`／`revoked_at`）**已存在** | M2 的書面同意直接用，**不必新建表**——這是 M2 成本比預期低的關鍵發現 |
| 能力握手 | `live_voice_server.py:2120` `?cap_evt=1` 機制 | 舊版 App 不給新工具，避免「AI 說設好了但 App 不支援」 |

### 2-2. 真正缺的（M1 要蓋的）

1. **care_episodes / care_notes 資料模型**（判斷二）。
2. **摘要單生成器**（`care_summary.py`）——讀多來源、輸出一頁。
3. **摘要單呈現面**（App 內大字版＋可出示的網頁版）。
4. **口袋問題的入帳**——寧寧說「我幫你記下來」之後，**現在真的沒有一個地方記**（只會進 memory_items 的模糊事實）。這是 M1 最小但最有感的一刀。
5. **不對稱鐵則的文字**（紅線 2）寫進 `chat_engine.py` CORE。

### 2-3. ⚠ 重大治理發現（沙利曼 · 這條會擋住 M2）

**`web/privacy.html:74` 白紙黑字對用戶承諾：**
> 「**用藥照片**：你可以為用藥提醒附上藥品照片，這些照片**只儲存在你的裝置本機**，不會上傳雲端，也不會與家人共享。」

而且 2026-07-16 Edward 才拍板跑 `018_strip_medication_photos.sql`，把過去漏傳上雲的照片清掉（起因：PR #101 修好前，照片隨 `routine_reminders.schedule` 上傳）。

**⇒ M2「拍照上傳病歷保管箱」直接牴觸這條已公開的承諾。** M2 不是「加一個上傳功能」，它是：
1. 隱私政策改版（照片/醫療文件的儲存位置與共享範圍要重寫）；
2. **既有用戶要重新告知與同意**（不能靜默改政策）；
3. 上傳路徑必須與「用藥提醒照片」在架構上分艙——舊承諾對舊功能仍然有效，新保管箱是另一個明確授權的容器，**不可以合流**，否則等於用新政策追溯覆蓋舊承諾；
4. 這條與紅線 4（特種個資書面同意）合併成 M2 的單一前置：**同意 + 政策改版 + 分艙**，三件一起做，缺一不可。

**這是本次規劃最有價值的發現**——它把 M2 的成本從「加功能」修正為「改契約」，也再次證明閘門制是對的：M1 沒證明價值前，不該去動用戶契約。

## 3. M1 產品功能拆解 × 技術掛點

> 設計總原則（蕪菁頭）：**零額外輸入、一頁、從寧寧口中遞出。** 任何需要長輩填表的設計一律退回。

### F1 · 口袋問題（最小、最有感、先做）
- **產品**：聊天中出現「這個要不要問醫生」的念頭 → 寧寧「我幫你記下來，下次看醫生第一個問」→ **真的存進 episode**；看診前一天推播「你之前想問的三件事，我幫你整理好了」。
- **技術**：`live_voice_server.py` 新增 tool `add_care_question`（比照既有 `set_clinic_reminder` 形狀＋`cap_evt` 握手）→ `app.js handleVoiceAction` 新增分支 → 寫 `care_notes(kind='question')`。文字線同步走 `server.py` 既有 action 管線。
- **為什麼先做這個**：它是 `安全能力補齊計畫` 批次 1 #6 的兌現、是 H1 假設最便宜的探針（有沒有人真的在問 → 就醫時刻痛不痛），且**不依賴摘要單完成**。

### F2 · 症狀時間軸（背景長出來、零輸入）
- **產品**：摘要單上的「主訴與變化」——「7/12 說膝蓋上下樓會痛 → 7/20 說走 5 分鐘就要停」。
- **技術**：背景任務讀 `memory_items` 中 `type=health_context` 且 `tier in (recent,long)` 的條目，按 `created_at` 排時間軸，**只做時序整理與去重，不做任何嚴重度判定**（紅線 3）。復用 `memory_engine.retrieve()` 的既有相似度能力做同一症狀的串接。
- **紅線落地**：輸出只有「他說了什麼、什麼時候說的」，**沒有加重/好轉/惡化這類評價詞**——那是醫師讀出來的，不是我們寫上去的。

### F3 · 就診摘要單（M1 核心產出）
- **版型（一頁、醫師 30 秒可讀，欄位順序即閱讀順序）**：
  1. **這次想問**（F1 的口袋問題，至多 3 條）
  2. **主訴與變化**（F2 時間軸，至多 5 筆）
  3. **在家量測**（`health_context.summarize_vitals`：跟他自己平常比，只列 notable）
  4. **用藥現況與實況**（藥單＋`medication_dose_events` 算出的實際服藥情形——**我們的獨家**）
  5. **生活狀態**（睡眠/活動/心情趨勢，來自既有 `wellbeing_signals`＋`mood_trend`）
  6. 頁尾固定聲明：**「本表由家屬/本人記錄整理，非醫療診斷。」**（紅線 1 的實體落地）
- **技術**：新模組 `engine/care_summary.py`（純函式、可單元測試，比照 `health_context.py` 的寫法）；生成掛背景（看診前一天由既有 briefing 排程觸發＋App 內可手動重生）；**不進語音熱路徑**。
- **鐵律繼承**：沒資料就誠實留白，**絕不補字**（`health_context` 的「沒資料回空」哲學直接繼承——一個以為自己有資料的模型會很樂意生一份出來）。

### F4 · 遞交（C0 · a2a 的 v0）
- **產品**：App 內「給醫生看」大字模式（長輩自己出示）＋一次性分享連結/QR（免安裝、醫師手機掃了就看網頁版）。
- **技術**：既有 `web/` 靜態頁 + 短效簽章連結（比照既有分享/匯出機制）；**預設 24 小時失效、可隨時撤銷**（沙利曼要求：遞交出去的東西必須收得回來）。
- **不做**：任何機構 API、任何 FHIR——那是 M4/M5。

### F5 · 就醫後閉環
- **產品**：回家後寧寧問「醫生今天怎麼說」→ 語音記重點 → 新藥/回診日**自動接進既有提醒系統**。
- **技術**：`care_notes(kind='doctor_note', source='user_reported')` → 觸發既有 `set_medication_reminder`／`set_clinic_reminder` 草稿流程（`用藥提醒-資料流設計` §一之2 已定的「草稿→家人確認」防聽錯藥名機制，直接複用）。
- **紅線**：記的是**用戶轉述**，`source` 標死，永遠不等同病歷，也不拿來做任何判斷。

### F6 · 不對稱鐵則入 CORE（安全加固、獨立可先上）
- `engine/chat_engine.py` CORE 新增子條款：可以往上推（建議就醫/掛急診），**永不往下擋**（不說「不用看醫生」「觀察就好」）。
- 現況查核：`nening_brain.py:44` 已有「絕不說『不用看醫生』」，但那是舊的單點人設檔；**CORE/RED 才是文字線與語音線共用的底盤**（`server.py` 與 `live_voice_server.py` 都吃 `eng.CORE + persona + eng.RED`），改一處兩線同時生效。
- 配 `engine/eval/` 新增鐵律測試條目（比照既有 `test_guardian_crisis.py` 與聊天品質劇本庫的做法）。

## 4. 資料模型草案（待與 Codex 對齊 schema 再落 migration）

```sql
-- 一次就醫的敘事主體
care_episodes(
  id, account_id, person_id, family_group_id,
  status,              -- brewing | scheduled | visited | following_up | closed
  chief_concern text,  -- 用戶自己的話，不是我們歸納的病名
  specialty_hint text, -- 衛教式科別建議（可空；不是分診）
  visit_id text,       -- 對應既有 munea.visits / routine_reminders
  visited_at, created_at, updated_at, deleted_at
)

-- episode 底下的所有條目
care_notes(
  id, episode_id, account_id, person_id,
  kind,    -- question(口袋問題) | symptom(症狀線索) | doctor_note(醫囑轉述) | attachment(M2 才開)
  content text,
  source,  -- chat_voice | chat_text | manual | derived(從既有資料算出)
  occurred_at, created_at, deleted_at
)
```
**設計註記**：
- `kind='attachment'` 欄位 **M1 不開**——留位置給 M2，但保管箱要走**獨立資料表與獨立同意**（§2-3 分艙要求），不是在這裡放檔案。
- RLS 從第一天就照 `RLS-子女授權同意分層` 的分層寫（`care_notes` 屬 L2-L3；`doctor_note` 敏感度比量測數字高，預設不進家人端全開）。
- 寫入一律收後端 `service_role`，client 只 select（沿用沙利曼 #6 稽核完整性要求）。
