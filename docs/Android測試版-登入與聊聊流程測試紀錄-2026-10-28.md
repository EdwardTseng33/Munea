## 怎麼做到「不用真鑰匙」

借用既有 `scripts/enable-ios-development-profile.mjs`（iOS 開發包腳本，本來就吃任意目標路徑），
加一道 `npm run android:dev-profile:direct`，只改 `npx cap sync android` 生成出來的
`android/app/src/main/assets/public/src/auth-config.js`，**沒有動 `web/` 裡任何一行 App 邏輯**。
Direct 模式會在 App 啟動時本機合成一個假登入 session（`window.MUNEA_DEV_CONFIG.autoSignIn = true`），
完全不呼叫真 Supabase、不需要任何密碼或金鑰；同時種一組假家人／假健康資料（`seedFixtures`），
讓首頁跟聊聊頁有內容可以看、可以點。

## 已知限制

1. **【App 層真發現，非測試腳本問題】direct 測試包的 `skipOnboarding` 蓋不到新版「開場三頁故事卡」**
   `web/src/app.js` 有兩套獨立的 onboarding 機制：舊版迎賓精靈用 `ONBOARDING_COMPLETED_KEY`
   （dev profile 的 `skipOnboarding: true` 有蓋到這個）；但 2026 年後新增的「三頁開場故事卡」
   （`openOnboardingIntro()`）用的是完全不同的 key（`ONBOARDING_INTRO_SEEN_KEY`），**dev profile
   完全沒蓋到**，而且它是用 `setTimeout(..., 2400)` 在 App 啟動約 2.4 秒後自動彈出、不看任何
   開發設定。這張故事卡的「下一步」按鈕剛好跟底部導覽「聊聊」分頁的位置重疊
   （故事卡按鈕 Y 軸 `2138-2283` vs 導覽列「聊聊」Y 軸 `2081-2330`，X 軸也重疊），所以：
   - 如果自動化腳本在故事卡彈出**之前**點到聊聊分頁 → 正常進入聊聊畫面（第 2 輪的情況）
   - 如果故事卡剛好在那個時間點彈出 → 腳本點到的其實是故事卡的「下一步」，不是聊聊分頁
     （第 3 輪的情況，已用座標重疊的 accessibility dump 證實）
   這跟環境無關、是 App 本身兩套 onboarding 機制沒對齊造成的，**建議之後開發包順手把這個新
   key 也種掉**，不只對自動化測試有幫助，也代表「真人測試帳號」每次登入都會被迫重看一次
   開場故事卡（除非他自己走完三頁按「開始」）。
2. **模擬器沒有真麥克風**（`-noaudio`）——即使成功點進「開始通話」，也預期連不上真正語音；
   這條路到目前為止還沒機會實際驗證畫面會顯示什麼（卡在上面第 1 點的時序問題）。
3. **這個 GitHub Actions runner image 的模擬器版本（37.2.12.0）不接受 `-prop persist.sys.*`
   開機參數**（只收 `qemu.*` 開頭），原本想釘 `zh-TW` locale 失敗；改成腳本同時給中英文候選
   字串繞過去（已驗證有效，見 `scripts/android-ui-tap-by-text.py`）。
4. **軟體渲染（swiftshader）在 CI 上偶發 GPU context 搶佔錯誤**
   （`DisplaySurfaceGlContextHelper context was preempted by others`），第 3 輪在等候通話按鈕
   那幾秒出現過一次，當下那張截圖直接是全黑——這類底層渲染抖動在軟體渲染的模擬器上是已知
   常見現象，不是 App 的問題。
5. **`--gateway`（真測試帳號走真 Supabase 登入＋總機領證）這條路這次沒測**：需要
   `MUNEA_TEST_ACCOUNT_EMAIL`／`MUNEA_TEST_ACCOUNT_PASSWORD` 這組 GitHub Actions secrets，
   目前沒有設定，所以沒有建立、也沒有嘗試自己生一組密碼放進去。
